一　缘起：为什么做「心桥」

这款产品最初的起点，是一份很朴素的需求：银行客户经理每天要维护大量客户，生日是其中成本最低、情感价值最高的触达节点，但靠 Excel、备忘录和人工记忆，总会漏。漏掉的不是一个日期，而是一段关系里「有人把我放在心上」的机会。

1.1　一个被反复提起的痛点

和很多工具的出发点一样，先有问题，后有产品。客户经理的痛点很具体：

  • 客户多，生日极易遗漏——表格和备忘录不会提前预警，重要 A 类客户错过生日触达，流失的是情感链接；
  • 数据合规风险高——姓名、账号、身份证、交易信息不能留存，但传统的表格式管理恰恰容易泄敏感信息；
  • 无沉淀、无追溯——没有统一维护记录，多年往来没有存档，公私联动缺少家属关系这类数据支撑。

第一版 PRD 就这样被写了出来：产品名暂叫「客户生日关怀助手」，定位是轻量化 Web 应用，目标用户是银行客户经理，核心闭环是「客户信息管理 → 生日自动识别 → 提前提醒 → 当天提醒 → 完成维护 → 沉淀记录」。

1.2　先想清楚，再写代码

写第一行代码之前，我强迫自己先输出四样东西：UI 原型、数据库 ER 图、技术架构方案、MVP 开发任务拆分。理由很简单：产品刚起步时，架构返工的代价远高于想清楚的时间成本。

这一阶段定下的关键决策后来几乎没被推翻过：

  • 隐私边界：只保存客户编号、简称、生日、性别、行业、等级、备注；身份证、账号、完整姓名、交易信息一律不碰；
  • 零成本：纯前端 + 浏览器本地数据库，没有服务器、没有收费数据库；
  • 极简操作：每天 30 秒到 2 分钟完成关怀，不增加工作量，只减少遗漏。

1.3　三个自我设限：隐私、零成本、极简

这三个设限在当时看起来是「约束」，回头看其实是产品最大的护城河：因为不碰敏感数据，合规风险天然为 0；因为零服务器，没有运维成本，也没有数据泄露面；因为极简，用户才愿意每天打开。

约束不是限制，是提前替你做完的决策。把「不做什么」想清楚，剩下的「做什么」就简单了。

二　从 0 到 1：最小闭环怎么搭

2.1　技术选型的克制

技术栈几乎是在第一版 PRD 里就定了：React + TypeScript + Vite 做前端，Dexie.js（IndexedDB）做本地存储，SheetJS 在浏览器里解析 Excel，再用 PWA 实现离线与安装。没有引入任何需要服务器的东西。

这套选型有个容易被忽略的好处：部署即静态托管。后来从 GitHub Pages 换到 Cloudflare Pages，几乎零成本迁移；断网也能用，客户经理在网点信号差、出差途中依然可以查看和记录。

2.2　「30 秒原则」与第一版骨架

第一版功能骨架围绕「打开就知道今天该干什么」设计：顶部三个统计（今日生日 / 未来 7 天 / A 类客户），今日生日卡片带「生成祝福」「完成维护」，未来 7 天列表按倒计时排列。整条路径被刻意压缩到一屏之内——看名单、发祝福、记结果，不来回跳页面。

「30 秒原则」后来成了我判断每个功能的尺子：如果这个功能不能在 30 秒内让用户感到「有用」，它就不该出现在首屏。

三　功能设计背后的思考（逐条复盘）

3.1　生日字段：从严格校验到智能解析

最早批量导入时，生日字段用的是严格格式校验，结果大量正常数据被判成「格式错误」。真实世界的 Excel 远比想象中混乱：有人写 1990/08/05，有人写 1990.08.05，有人写 1990年8月5日，有人只写 8月5日，甚至有人贴的是 Excel 日期序列号（一串数字）。

我得到的教训是：校验的终点不是「格式对不对」，而是「数据能不能用」。于是把策略改成智能解析：先尝试解析，能解析就统一转成 YYYY-MM-DD 或 MM-DD，解析不了的才报错，并且给出可读的行号提示。最终支持 8 种常见格式，还保留了「无年份生日」——因为大量存量客户只知道月日，不知道年份。

3.2　提醒设计：提前 7 天与「当天三次」的分寸

提醒分两级：提前 7 天让客户经理来得及准备（订花、备礼、约时间），当天 A 类客户三次（09:00 / 10:00 / 14:00）是针对重点客户的一次触达不到位、多给几次机会。

这里有一个诚实的插曲：「当天三次」最终被暂缓上线了。因为产品是纯网页应用，没有系统通知权限，所谓「定时提醒」只能在打开应用时看到，本质上无法真正定时触达。与其挂着一个名不副实的功能，不如先把模块下线，在 PRD 和用户手册里保留说明、注明原因，等接入推送能力再恢复。

承认「现在做不到」，比假装「已经做到」更难，也更值得。功能可以暂缓，信任不能透支。

另一个细节是「提醒状态不落库」：已完成/已联系的状态由「当天是否存在维护记录」动态派生，而不是存一个布尔值。这样跨年不会过期——去年标过已联系，今年生日依然会重新提醒。

3.3　祝福生成：为什么不调 AI

很多人会默认「生成祝福语 = 调大模型」。我的选择恰恰相反：用本地规则引擎，按等级、行业、备注关键词做随机组合。

理由有三个：隐私（客户信息不出本机，不把客户资料发给第三方）、零成本（没有 API 费用）、离线可用（断网也能生成）。规则引擎还有一个隐藏优势：结果可稳定复现，字数可控（30–80 字），还能过滤「尊敬的、衷心祝愿」这类生硬措辞——像人写的微信，而不是模板。

备注里藏着的细节会被识别出来：茶文化、授信、理财、对公、私行、创业、合作年限……这些关键词让祝福从「群发」变成「记得你」。

3.4　家属关系：客户关系不是单点，是一张网

做家属关系的最初动机是公私联动：企业主的配偶、子女、父母，可能是实控人、接班人或关键决策影响者。一个客户背后往往是一整个家族的业务版图。

家属关系经历了三次迭代：先是简单的「夫妻 / 子女 / 父母」标签；然后加了搜索关联——按客户编号或姓名把家属关联到系统内已有客户，并做双向自动同步（A 添加「儿子 B」，B 的档案自动出现「父亲 A」）；最后把关系具体化：老公 / 老婆 / 儿子 / 女儿 / 父亲 / 母亲，并且反向关系会根据主人性别自动判断（刘先生登记「儿子」，对方档案显示「父亲 刘先生」）。

家属不一定是存量客户，所以自由登记也支持：填写姓名、生日、备注即可，无需客户编号；填了生日就自动进入和标准客户一样的提醒序列——家属的生日同样是关怀节点。

3.5　备注跟随关联人：让信息属于它该属于的人

这个功能来自一个真实的乌龙：你在张小姐的档案里为父亲张先生写下「喜欢雪茄」，结果这条备注被复制到了张先生档案里「子女张小姐」的名下——下次送礼很可能把雪茄送给张小姐。

修复的思路很简单也很重要：关于「他」的信息，就属于「他」。为关联人填写的备注，会同步到该关联人本人的信息里，而不是复制到双方的关系条目上。信息放对位置，人才不会张冠李戴。

3.6　生日画像标签：年龄、属相、本命年、星座

生日里藏着年份，就是一座画像金矿：年龄决定称呼分寸与关怀深度；属相与「本命年」直接服务送礼——马年给属马的客户备红绳、转运物，是低成本高记忆点的关怀；星座是聊天破冰的自然话题。

这条规则有一个刻意设计的边界：只在生日含年份时显示标签。无年份生日宁可不显示，也不错误推算——闹出年龄笑话比没有标签更伤。

3.7　星标：价值等级之外的「关注维度」

A/B/C 等级衡量的是「客户价值」，但「谁值得我多花心思」是另一种判断。某位 C 类客户可能是重要的引荐人，某位客户正处在关键业务节点——星标就是把这第二种判断交还给客户经理，与等级解耦，随时置顶、随时筛选。

3.8　演示模式：让人 30 秒看懂产品

空产品没法演示。于是我把一份 34 位客户的完整演示数据（含家属关系、维护记录、星标、画像标签）直接内嵌进应用，设置页一个开关即可加载。

这里有个容易被忽略的工程决策：演示数据与真实数据用两个独立的 IndexedDB 数据库隔离。开启演示模式切到演示库，关闭切回真实库，两边互不干扰——演示得再欢，也不会污染客户经理的真实数据。

3.9　分页与多维筛选：客户多了以后怎么办

当客户量上来，一屏渲染全部客户既不流畅也难浏览。于是客户列表改为按距离生日倒计时正序 + 每页 20 条分页，底部统计总数。筛选从零散的按钮整合成下拉菜单：等级、行业、星标、生日月份、星座、属相——比如「属马 + 12 月」可以一次筛出本命年客户批量备礼。

3.10　性别智能识别：少填一个字的细节

录入「刘先生」时，性别不该再手选一次。系统会从简称里识别关键词（先生 / 哥 / 男士 / 男生 → 男；女士 / 姐 / 妹 / 女生 → 女），识别结果可自由修改，修改后不再覆盖。一个「少填一个字」的细节，就是产品感。

3.11　撤销导入与三次确认：让人敢用

批量导入是迁移成本最高的动作，也是最容易误操作的动作。所以导入后可以一键撤销（删除新增客户、还原被覆盖数据）；清空数据则要三次确认。一个让操作可回退，一个让破坏性操作不可轻易触发——敢用，才会用。

3.12　导出提醒：把备份嵌入工作流

本地存储的最大风险不是「没数据」，而是「数据悄悄没了」——手机清内存、清历史、换机都可能。于是完成每次关怀后，应用会弹出一次数据备份提醒（每天最多一次，不打扰），引导去导出；导出文件还会跳过空单元格、压缩列宽，让备份更小更快。

四　文档与门面：工具背后的「说明书」

4.1　PRD 与用户手册：写给谁看

产品做到一定程度，我发现真正拉开差距的不是功能，而是「有没有把为什么讲清楚」。于是产出了两套文档：PRD（给复刻者与未来的自己看，含需求编号、验收标准、设计考量）和用户手册（给使用者看，配真实截图，甚至生成 PDF 内置到官网供下载）。

PRD 有一版专门补了「设计考量」：每个功能都回答一次「为什么存在」。比如属相标签是为了送礼与祝福，星标是为了表达关注，备注跟随关联人是为了送礼不错人。文档不是摆设，是产品决策的存档。

4.2　设计考量：每个功能都要回答「为什么」

「先解决有没有，再解决好不好」是我在文档里写下的总纲。对照表里的每一条，几乎都是被真实问题逼出来的：

  • 一打开就看到「今天该维护谁」→ 减少决策成本；
  • 生日只填月日也可以 → 存量数据挡在门外等于没导入；
  • 状态由当天记录派生 → 不落库就不会跨年过期；
  • 演示数据双库隔离 → 演示不能污染真实数据；
  • 完成关怀后提醒导出 → 把备份嵌入最顺手的时刻。

4.3　官网：先有产品，再有门面

产品稳定后，官网才值得做。官网保留了原始的叙事逻辑（行业痛点 → 核心价值 → 真实场景 → 快速上手 → 功能矩阵 → 技术安全），但内容全部按最新功能重写，删掉了截图模拟，改成移动端优先、纯 CSS 绘制的产品首页演示。三时段提醒这类暂缓功能，在官网里加了星号和小字说明——门面也要诚实。

五　踩过的坑与修正

5.1　移动端聚焦缩放：16px 规则

iPhone 上点击搜索框，页面会突然放大——这是 iOS Safari 的经典行为：输入框字号小于 16px 时会自动缩放。修复不靠禁用缩放（那会伤害可访问性），而是把所有输入控件字号统一提升到 16px。一个像素级的规范，解决一个体验级的问题。

5.2　Cloudflare Direct Upload 的 404 之谜

第一次部署到 Cloudflare Pages，接口返回「部署成功」，线上却是一片 404。反复尝试了四种 multipart 字段格式都不行，最后改用官方 Wrangler CLI——一次通过。教训：能用官方工具就别手写协议细节，省下的时间足以再迭代一个功能。

5.3　暂缓上线：承认「现在做不到」

「当天提醒（A 类三次）」因为没有系统通知权限，从产品中下线，但 PRD、用户手册保留说明并注明原因，官网加星号标注。功能下线不是失败，是把「产品诚实」当作上线标准。

六　一些产品思考

6.1　工具的价值在于减少遗漏

心桥没有发明新需求，它只是让「记得」这件事变得可靠。好的工具不制造焦虑，而是接管那些人不擅长的事（记日期、算倒计时、想话术），把人的精力留给真正需要人的部分（一个电话、一句问候）。

6.2　边界感：什么该自动，什么该问人

这条产品里有一条反复出现的边界：系统可以提醒、可以生成、可以记录，但不代替人做决定——祝福要人确认，记录要人填写，清空要三次确认。自动与打扰之间只有一线之隔，好的系统知道什么时候该停下来问人。

6.3　审美与克制

从橙白主题到 16px 输入框，从「心的桥梁」这句 slogan 到官网上的星号脚注，克制贯穿始终：能少一个按钮就少一个，能少一个字段就少一个，能诚实标注就不含糊。产品最后的质感，往往来自这些「少」的决定。

6.4　下一步

接入系统推送/通知能力后恢复「当天三次」提醒；基于用户与团队字段做日报/周报汇总；以及继续打磨那些让客户经理「愿意每天打开」的细节。

结语

回头整理这段开发记录，最感慨的不是写了多少功能，而是每个功能几乎都对应一次真实的取舍：隐私 vs 便利、完整 vs 极简、自动 vs 打扰、现在 vs 以后。

产品叫「心桥」，slogan 是「心的桥梁」。它最终想做的事其实很小：让客户经理记得住，让客户被放在心上。

工具不创造关系，工具让关系不被忘记。

如果这篇文章里有一个想法能帮到你，那最好的是这一句：先想清楚为什么，再决定做什么；承认做不到的，比假装做到更接近做好。
