AI Agent

一种能自己规划、调用工具、执行动作来完成目标的 AI 系统。这篇记录我对 Agent 架构的理解，以及做 LifeOS 时踩过的坑。

更新于 2026.07

什么是 Agent

传统 chatbot 是「你问一句，它答一句」；Agent 的区别在于它手里有了动作。给它一个目标，它会自己拆步骤、决定调用什么工具、执行、看结果、再决定下一步，直到目标达成或主动停下来问人。

判断一个东西是不是 Agent，看三件事：有没有目标驱动的循环、能不能接触外部世界（工具/API）、以及是否有停下来求助的边界感。

Agent 架构总览

一个能用的 Agent 通常由四块组成，它们之间是依次咬合的关系：

模块职责关键问题
Planner把目标拆成可执行的计划拆多细？何时重规划？
Memory记住上下文与历史记什么？忘什么？
Tool把能力外接到世界暴露哪些？如何防错？
Execution从计划到动作并回收结果谁来确认危险操作？

Planner：把目标拆成可执行的计划

Planner 不直接干活，它产出「下一步做什么」的清单。好的 Planner 不是一次拆到最细，而是拆到「能安全交给 Tool 执行」的粒度就停——太粗则 Tool 无从下手，太细则失去灵活性。

模型定不下来，代码写得越快返工越多。Planner 的提示词和结构，值得花最多时间打磨。

实践中我们让 Planner 输出带依赖关系的步骤，并在每步执行后判断是否要重规划：当真实结果偏离预期，重新生成后续步骤，而不是硬走原计划。

Memory：让 Agent 记住上下文

Memory 分两层：短期（本轮对话的上下文窗口）和长期（跨会话沉淀的事实、偏好、历史决策）。长期记忆是 Agent 从「一次性工具」变成「长期搭档」的关键。

  • 写什么：用户的稳定偏好、已完成的任务、踩过的坑。
  • 忘什么：临时中间态、一次性的脏数据。
  • 怎么取：按相关性检索，而不是全量塞进上下文。

Tool：把能力外接到世界

Tool 是 Agent 与真实世界之间的接口——查日历、下单、发消息、读数据库。暴露 Tool 时最该想清楚的是失败模式：每个 Tool 都可能出错、超时、或产生不可逆后果。

// Tool 的最小契约
{ name, description, input_schema,
  execute(args) -> { ok, data?, error? } }

设计原则：只读操作可自动执行；写操作、涉及钱/隐私的操作，必须留给人确认。LifeOS 里系统可以把订单下到「待付款」，但绝不自动扣款——这条硬边界，决定了系统是帮手还是麻烦。

Execution：从计划到动作

Execution 是真正「动手」的环节：调用 Tool、拿到结果、把结果喂回 Planner 决定下一步。它最容易被忽略，却最决定体验——节奏、可读性、异常时的表达，全是产品问题。

Execution 循环要在「自动」与「打扰」之间找分寸：能自己搞定的不打扰人，该问人的绝不替人做主。这条线，决定了用户是信任它还是害怕它。
